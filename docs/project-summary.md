# Instance Health: Project Summary

Status as of 2026-11-09, taken from the repository, the git history and `docs/check-catalogue.md` (the source of truth for every check). Intended as knowledge for a claude.ai Project.

## 1. What it is

ServiceNow Fluent app **Instance Health** (scope `x_bits2_inst_hlth`, now-sdk 4.14.0, by BitHawk). It delivers Instance Scan checks that evaluate instance health in three areas: administration, maintenance and performance. The results are condensed into a health score with a dashboard.

- Dev instance: `bithawkdemo1`, auth alias `but-o`.
- Build `npm run build`, deploy `npm run deploy` (only on the user's request).
- Everything built so far (2026-11-05 to 2026-11-06) is deployed to bithawkdemo1.

## 2. Result in numbers

- **73 scan checks** `IH-001` to `IH-073`, in three files: `administration.now.ts`, `maintenance.now.ts`, `performance.now.ts` (`src/fluent/scan-checks/`).
- **Validation:** 60 checks `validated` (confirmed by a test record or real findings, no wrong finding). 13 checks `built`, because they find nothing on the demo instance and a test would need instance-wide settings, an upgrade or 5 million rows: IH-007, 019, 022, 031, 036, 050, 051, 056, 058, 060, 061, 067, 068.
- **Priorities** (by impact on instance health): 13 × priority 1, 31 × priority 2, 29 × priority 3.
- **Suite runs:** SR00014613 (first run, 770 findings, 66 of 73 checks as expected) and SR00014619 (second run, 946 findings, no failed check, every positive test record found, no negative one).
- **Health score:** first values 60 (knock-out cap, uncapped about 81 to 83). Priority 1/2/3 sub-scores 76.9 / 81.3 / 87.5. Category scores: security 53.1, performance 93.1, manageability 89.8, upgradability 67.8.

## 4. Health score rules (agreed 2026-11-06)

- **Check score (0 to 100):** 100 − findings × points per finding, at least 0. Points per finding: P1 20, P2 5, P3 2. Setting checks (one finding means a setting is wrong: IH-007, 019, 021, 022, 031, 033, 036, 050, 051, 058, 067) score 0 with the first finding. Share checks (IH-056, IH-070) use the share.
- **Health score:** weighted average of the check scores, weight 5 for P1, 3 for P2, 1 for P3.
- **Knock-out cap:** if a P1 check scores 0, the health score is at most 60 (`score_uncapped` keeps the raw value).
- **Sub-scores** per priority and per category (security, performance, manageability, upgradability).
- Failed or unrun checks are not counted and are listed in `checks_failed`.
- Open idea: for checks with large populations (IH-017, 030, 042, 064) base the score on the share, so instance size does not distort it.

## 5. Decisions and conventions

- **Check numbering (2026-11-06):** visible IDs `IH-NNN` are consecutive without gaps. Dropped checks are closed up by renaming only (`tools/renumber-checks.js`). `$id` keys (`ih-KKK-…`) and export names never change, so sys_ids, findings and suite links stay. The next free key number is 081 (as of 2026-11-06).
- **Priorities by impact (2026-11-06):** 1 = instance-wide or all users, data exposure, breaks upgrades. 2 = single processes, users or areas. 3 = everything else.
- **Every finding links to the record to act on** (2026-11-05), through `engine.finding.setCurrentSource(...)`. For helper tables the real record is resolved.
- **Generated records excluded (2026-11-06):** GAF scheduled scripts and OneExtend mappings never count as custom (`IHScanUtil.GENERATED_TABLES`).
- **Dropped checks:** Java package collection mode, priority 1 skipped upgrade items, scheduled reports as invalid or inactive user (covered by IH-047/048), list layouts with duplicate positions.
- Scripts are inline ES5 strings. Prefer a condition-only TableCheck when every matching record is a finding.
- Workflow per batch: specify in the catalogue → build → deploy (user approval) → run on bithawkdemo1 and review → tune thresholds, mark `validated`.

## 6. Lessons learned (platform and SDK)

- The scan engine skips the base table `task`; a TableCheck on `task` only covers child tables. Use a ScriptOnlyCheck that queries the table itself (IH-049, IH-054).
- The suite scan did not evaluate some records that a point scan did (IH-016, IH-037); these became ScriptOnlyChecks.
- `GlideAggregate.addActiveQuery()` is not allowed in the app scope; use `addQuery('active', true)`.
- `Record()` sets no platform defaults: set `active: true` and display fields explicitly (the menu modules were hidden at first).
- Fluent files allow no loops. `Table` role properties create no ACLs in 4.14.0, so write `Acl()` records.
- SDK 4.14.0 wrote unresolved component names (`filter`, `list-simple`) into dashboard widgets. The fix is to use the platform sys_ids.
- A business rule on `scan_result` is not possible (`configuration_access=0`), so a scheduled job calculates the score.
- Test data: records follow the user's current application, so the scripts switch to global and restore the app. A report counts as public only with the `public` role. `sys_script.name` holds 40 characters. `now-sdk exec` sometimes reports an error although the script ran: check the instance before repeating.
- Changing a check's type changes its table, so it gets a new key number and the build deletes the old record.
